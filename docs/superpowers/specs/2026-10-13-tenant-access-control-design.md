# 租户归属性与可见性

## 1. 两类权限，一个访问控制模型

归属性和可见性是权限的两种分类，都由新的通用访问控制模型配置、计算和执行：

- **归属性规则**：授予读取和写入的数据范围。实际能执行哪些操作、能写哪些字段，仍受角色 ACL 约束。
- **可见性规则**：只授予读取的数据范围，不授予写入权限。

记录继续用 `tenantId` 保存实际归属。匹配一条归属性授权规则不改变记录归属；规则中的“归属性权限”与数据字段的归属值分别承担授权和记录归属职责。

例如，总部录入涉及誉良浙江分公司的单据。总部通过归属性规则获得读写范围，誉良分公司通过可见性规则看到相关单据，但不能写；单据归属始终为总部。

不再保留“旧租户模式决定写权限，新规则额外扩展读取”的双轨实现。本租户、父级租户、指定租户等都只是同一模型可以表达的条件。

## 2. 权限计算

记 G 为匹配归属性规则的记录范围，V 为匹配可见性规则的记录范围：

```text
可读取 = 角色读取权限及数据范围 且（G 或 V）且 请求筛选条件
可写入 = 角色对应写操作权限及数据范围 且 G
```

两类规则各自取并集。只命中可见性不能写；同时命中两类时按归属性授权判断写权限。不新增按新增、修改、删除细分的租户规则；这些操作的差异继续由角色权限及已有业务约束处理。

没有匹配规则时拒绝访问，不能回退到旧过滤放行。规则异常、变量缺失或不支持的条件不能变成空过滤。共享表或匿名读取是否需要租户上下文，取决于规则本身和 ACL，不能一概强求。

新增记录的归属仍由服务端设置，默认当前租户；补齐归属后，候选记录必须匹配归属性规则，只有可见性不能新增。普通修改不能重写 `tenantId`。归属转移、历史首次认领、不可删除状态等数据约束不因匹配规则而失效。

## 3. 一条规则需要什么

在租户管理的数据表配置中使用同一规则编辑器，每条规则提供：

1. 名称及启用状态。
2. 权限分类：归属性或可见性。
3. 访问者条件：当前租户、用户、角色等可信身份条件。
4. 数据条件：哪些记录符合，支持字段及关联关系筛选。

数据源及表是规则的配置范围。指定租户、本租户、父级、子级等均通过编辑器的条件表达，不再各自维护独立名单或过滤分支。不把某些业务公司、项目或表名写进框架。

例如：

| 分类 | 条件示例 | 含义 |
| --- | --- | --- |
| 归属性 | 记录归属等于当前租户 | 本租户获得读写范围 |
| 归属性 | 当前租户是记录归属租户的祖先或自身 | 父级及所属租户获得读写范围 |
| 可见性 | 单据参与方中存在业务租户等于当前租户的组织 | 相关租户获得读取范围 |
| 可见性 | 访问者为配置选中的租户，且记录符合配置条件 | 特定租户查看特定记录 |

这些是规则示例和编辑器可用模板，实际均交给同一个模型执行。界面可以提供模板方便配置，但模板不能成为模型之外的授权机制。

多对多条件必须能表达“同一关联项同时满足”。有限关联路径、受控变量和字段操作符通过元数据验证；不支持任意脚本或 SQL 作为规则。

业务组织代表哪个租户必须有明确关系，不能默认用组织记录的 `tenantId` 判断。组织记录本身也可能归属总部。框架允许选择实际关联路径，不解析名称猜测。

按当前业务关系计算范围，关系变化后旧单据范围随之变化。需要保留开单时关系的业务，在单据保存稳定的参与方关系。维护授权关系的权限仍由 ACL 控制。

## 4. 原有配置如何迁移

迁移保留原来允许的行为，执行机制统一替换：

| 原有配置 | 转换结果 |
| --- | --- |
| 所有租户可见 | 一条不限制租户的归属性规则；仍受角色 ACL 限制 |
| 仅当前租户可见 | 一条“记录归属等于当前租户”的归属性规则 |
| 当前租户及其父级租户可见 | 一条“所属租户及祖先可访问”的归属性规则 |
| 可见历史数据的租户名单 | 一条“访问者属于原名单，且记录未归属”的可见性规则 |
| 允许编辑历史数据 | 配合历史读取授权转换为允许首次认领的归属性规则，并保留原子认领约束 |

名单和模式迁移后只作为规则内容及模板存在，不继续独立决定访问。历史编辑关闭时不生成相应归属性授权；保持原有只读提示。即使以后配置了历史归属性授权，首次认领约束仍须成立，不能直接删除未归属记录。

分阶段按表迁移、验收。每张表只使用一种执行机制；已迁移表读写全部使用新模型。尚未迁移表暂用旧机制是上线过渡，不是最终设计。

配置回退和规则修改不撤销已发生的数据认领，也不改写业务记录的实际归属。共享表不因为迁移而强行增加或查询 `tenantId`。

## 5. 关联、工作流和汇总

关联读取使用 G 或 V，关联写入使用 G。仅引用已有对象沿用现有协议：来源可写、目标可读。实际修改、删除关联目标时检查目标的 G；不能因为目标可见就嵌套写入。已经存在且未变化的关联不能被误判为新增引用或目标修改。

能看单据不自动开放全部合同、项目或客户资料。必要关联表也通过同一模型配置范围，不增加全局递归授权。明细、附件读取及下载接入相应记录的读取范围；上传、替换、删除仍检查归属性授权。

关联展开只处理本次请求实际使用的关系路径，由入口显式提交查询计划。已迁移目标表按自己的读取范围过滤；未迁移目标表保持原来的租户机制。隐藏的单值关联返回 `null`，多值关联只返回可读项；单纯展开关联不能因此丢掉本来可读的根记录。过滤应在数据库查询阶段完成，不能取出后再逐项查权限。

用户通过关联字段筛选、排序、分组或求和时，也只能使用该目标表允许读取的数据。正向匹配在可读目标中判断，否定存在表示“不存在可读的匹配项”，不能用隐藏目标的有无反推数据。排序将不可读目标按空值处理；明细汇总过滤不可读明细。适配器不支持某种组合时返回明确错误，不能退回未过滤的查询。以上只补齐租户 G/V 范围，保持现有角色关联 ACL 协议，不恢复已经撤销的全局关联 ACL 改造。

规则自身使用的关联关系是管理员选定的授权依据，服务端可以在授权判断内部读取这些事实，不递归套用被引用表的规则，否则容易形成循环或因隐藏事实误拒绝。该内部查询只能计算是否匹配，不能把事实内容、数量或关联对象加入响应；普通页面查询仍执行目标表的读取范围。

保留 `/_/` 直接查询关联目标的协议，只略过不存在的来源记录检查，继续计算目标权限。

列表、详情、关联读取、计数、汇总、图表和导出采用同一读取范围。关联匹配多项时只能计算一次根记录，不重复计数或求和。

工作流查询使用读取范围，写节点使用归属性范围。按归属分派的定时任务继续按记录实际归属处理；不能因为多个租户获得可见性就重复处理同一单据。重试、延时和后台任务保留可信上下文。

原始 SQL、SQL 视图及外部数据源需要明确适配，不宣称普通接口过滤自动覆盖这些路径。

## 6. 实现方式

在 `module-tenant` 提供统一规则服务，输入可信身份、数据源和表，生成归属性范围 G 及可见性范围 V。各入口读取时使用 G 或 V，写入时只使用 G，并与各自 ACL 及数据约束共同检查。

同一规则解析器处理两类规则，不新增独立写规则系统，也不维护旧模式过滤的隐藏兜底。公共服务通过插件公开契约接入，避免工作流对租户插件入口的运行时循环依赖。

配置优先沿用现有数据表 `options` 持久化方式，保存两类规则，按数据源及表稳定标识加载。迁移后的旧配置只用于回退记录或生成模板，不能继续与新模型同时决定权限。管理员保存配置时验证条件、依赖及并发修改，普通业务用户不能更改规则。

当前核心关联筛选主要采用 JOIN，需要先验证模型条件的查询计划和去重。不能先加载大量关联 ID，也不能逐条查权限；不恢复全局关联 Scope 或 Eager Loading 守卫。必要核心能力以调用方显式启用的通用查询接口提供。

规则范围、ACL 及请求筛选分别保留来源，避免处理租户条件时误删其他过滤。缓存不能在不同身份、数据源或规则配置间错误复用。

## 7. 开发与验收

先实现和验证模型的条件计算及查询性能，再迁移一张试点表的读写，随后接入配置页面、关联、汇总、导入导出及工作流。每阶段按行为独立提交。

| 场景 | 预期 |
| --- | --- |
| 总部录单，分公司仅有可见性规则 | 总部可读写，分公司可读不可写，归属不变 |
| 分公司匹配归属性规则 | 在 ACL 允许下可写，不因此改变实际归属 |
| 无关单据及兄弟租户 | 未匹配规则时不可访问 |
| 父级授权、共享表及历史名单迁移 | 规则表达与原行为等价，无旧分支重复执行 |
| 两类同时命中 | 可读；写权限来自归属性规则 |
| 角色无操作或字段权限 | 模型不能绕过角色限制 |
| 多条规则及多对多同时匹配 | 列表、总数和金额不重复 |
| 列表、详情、关联、汇总、导出 | 读取范围一致 |
| 可见关联目标与嵌套写入 | 只读不能转成写权限 |
| 历史首次编辑及并发认领 | 原子认领；只读、引用不改变归属 |
| 工作流及定时处理 | 读写分类一致，归属型任务不重复处理 |
| 占位符及同名外部表 | 正确识别协议，不混用数据源 |
| 无匹配规则或配置异常 | 不通过旧机制放行 |

使用恢复后的实际业务数据复核仓库筛选、合同搜索、审批详情及底部汇总的耗时、SQL 次数和计划。

## 8. 配置结构与条件表达

每张表的 `options.tenantAccess` 保存一份配置，不再分别保存两套执行逻辑：

| 字段 | 用途 |
| --- | --- |
| `schemaVersion` | 条件结构版本，首版为 1 |
| `revision` | 保存时递增，用于并发编辑检查及缓存失效 |
| `ownership.enabled` | 记录是否具有实际租户归属；只影响归属字段管理，不直接授权 |
| `rules` | 归属性及可见性规则列表 |

每条规则保存 `id`、`name`、`enabled`、`category`、`subject`、`condition`。分类只允许 `ownership`（归属性）和 `visibility`（可见性）。`subject` 判断访问者，`condition` 判断记录，二者同时成立才匹配。

这份配置没有操作列表、允许/拒绝优先级和字段编辑清单。需要排除某类数据时，在允许范围的条件中表达；角色已有的字段和操作设置继续承担相应职责。

条件使用经过校验的结构化表达式，避免自由文本脚本：

| 表达式 | 语义 |
| --- | --- |
| `all` / `any` / `not` | 同时满足、任一满足、条件取反 |
| `compare` | 字段或身份变量与固定值、身份变量比较，操作符按字段类型选择 |
| `isNull` | 明确判断空值，不依赖比较运算的 SQL NULL 行为 |
| `exists` | 某关联中存在一项满足内部完整条件，支持单值及多值关系 |
| `tenantRelation` | 服务端校验后的租户相同、祖先或后代关系，包括自身与否明确设置 |
| `constant` | 显式全范围或空范围，用于共享表和默认拒绝 |

值分为固定值、当前记录字段和可信上下文变量。`exists` 内的字段相对该关联对象；同一项的多个条件放在同一个 `exists` 内。首版不开放任意两表字段比较；记录字段与当前身份变量比较足以表达主要业务需求。

以下为拟定配置格式，表示本租户读写授权。它是新模型的规格示例，当前接口尚不接受这种结构：

```json
{
  "schemaVersion": 1,
  "revision": 1,
  "ownership": { "enabled": true },
  "rules": [
    {
      "id": "owner-tenant",
      "name": "所属租户可读写",
      "enabled": true,
      "category": "ownership",
      "subject": { "type": "constant", "value": true },
      "condition": {
        "type": "compare",
        "operator": "eq",
        "left": { "type": "field", "path": "tenantId" },
        "right": { "type": "context", "path": "tenant.id" }
      }
    }
  ]
}
```

`subject` 使用相同表达式，但仅能引用上下文及固定值，不能读取候选记录。逻辑组用 `children`，`not` 用 `child`；`exists` 保存 `path` 和 `condition`；`tenantRelation` 保存访问者、记录侧租户值、关系类型及是否包括自身。固定值使用 `{ "type": "literal", "value": ... }`。字段路径由元数据校验后解析，禁止把输入路径直接拼进 SQL。

字段操作符首版支持等于、不等于、大小比较、集合包含、字符串包含及明确的空值判断；按字段类型提供选项。租户 ID 统一规范化后比较，不能让数字与字符串形式不一致导致误拒绝。

上下文变量只包含服务端已验证的当前用户 ID、当前角色、当前租户及有效层级信息，不开放任意请求参数或请求头取值。租户关系通过租户元数据核实，停用租户不能靠旧的客户端缓存继续获得访问。

首版关联路径最多 3 层，不支持跨数据源关联或循环调用其他表的访问规则。空规则列表、空逻辑组和缺失条件不能解释为全范围；需要全范围必须明确使用 `constant: true`。缺失变量属于配置或上下文错误，在计算前拒绝，不能被 `not` 反转成放行。

条件采用 SQL 三值逻辑：比较遇到数据库 NULL 得到“未知”，`not(未知)` 仍为未知；`all`、`any` 按相同逻辑组合，最终只有“真”授予权限。内存中的候选记录检查必须使用相同语义，不能先把未知变成假再取反。需要匹配空值必须使用 `isNull`；`exists` 内只把条件为真的关联项视为匹配。

表结构、字段及关联类型改变前验证受影响规则。规则依赖服务端元数据中的稳定标识，不能让删除后同名新表继承旧权限。

## 9. 新增及修改的具体执行约定

**新增**先过滤角色禁止的输入、设置实际归属，再检查候选记录是否满足 G。条件依赖候选明细时，在事务中检查实际准备写入的关系，失败全部回滚；外部回调和工作流事件只能在提交后发出。

**修改和删除**检查数据库中的修改前记录是否满足 G，校验与写入在同一事务中。不能根据请求中伪造的项目或租户值让原本无权修改的记录获得权限。

修改后不要求继续命中同一条规则。例如“草稿可编辑”的记录正常提交后，可以退出当前人的编辑范围。这不是新的一类授权，也不增加“写入后条件”配置。普通修改仍禁止归属转移；能改变授权范围的业务关系受其所属对象 ACL 与归属性权限保护。管理员配置 G 时需明确：授予编辑意味着允许在现有字段权限内改变该记录，包括使其离开当前范围。

写入已成功但操作者随后不再可读时，返回成功及允许公开的最小结果，不自动重新查询完整数据后误报失败。

授权条件依赖可变关联时，只锁根记录不足以防止并发变化。首个 PostgreSQL 原型采用串行化事务，将授权事实读取、根记录检查及全部关系写入放在同一事务中；必须覆盖关系新增、删除、修改和否定存在。并发撤权与写入可以按某个合法先后顺序完成，或有一方因冲突失败；撤权已提交后才开始的写入必须使用新事实。不能宣称所有重叠请求都一定由撤权优先。

序列化冲突默认回滚并返回可重试提示；只有确认整个业务事务可安全重复时才自动重试，不能单独重试授权检查或重复发送业务通知。已有事务不能升级隔离级别时，应在外层建立符合要求的事务，无法满足则拒绝该写入口。根字段规则仍使用事务内条件校验及根记录锁，不把所有业务写入统一升级为串行化。其他数据库适配器需通过同等并发测试才能启用关系型 G；V 不因缺少写入适配能力而被禁止。

明确指定多个目标的写请求中，存在不匹配 G 的目标时整体拒绝并回滚。筛选式批量操作在角色范围、G 和请求筛选的交集内执行，保持原有接口语义；不能借这次改造默默把所有批量接口改成另一种行为。

关联操作按真实写入位置分类：

| 操作实际影响 | 必要范围 |
| --- | --- |
| 修改来源记录的单值外键 | 来源 G，目标 G 或 V |
| 仅新增、移除普通多对多连接 | 来源 G，目标 G 或 V；按已登记的关系操作执行 |
| 有独立业务字段或归属的中间记录 | 另外检查中间记录的 G，不能当作普通连接放行 |
| 一对多绑定、解除绑定或移动 | 会修改目标外键，来源及所有实际变化目标均需 G，包括被 `set` 隐式移除的旧目标 |
| 嵌套更新、目标删除、级联删除、排序移动 | 所有实际写入对象均需 G 和对应角色权限 |

这一区分来自当前核心 Repository 的实际行为：`HasManyRepository.set/add` 会调用目标外键写入；多对多 `destroy` 也可能删除目标记录，不能只按按钮名称判断是否仅解绑。

## 10. 历史数据、ACL 和后台执行的迁移细节

历史数据有 G 时允许首次编辑认领，没有 G 但有 V 时只读。认领必须有有效当前租户、执行 null 到当前租户的原子检查，并使用数据库锁避免两人同时认领；认领后不保证原来的历史规则继续匹配。直接删除未归属数据仍禁止。`ownership.enabled = false` 的表不把无归属值当作需认领的历史数据。

当前代码还登记了 `dataSourcesRolesResourcesScopes` 中 `key=tenant` 的“当前租户记录”角色范围。若原样保留为 `tenantId = 当前租户` 的固定条件，V 即使命中也可能被 ACL 挡住。因此：

- 对已迁移表，该内置范围改为委托统一模型：读取使用 G 或 V，写入使用 G；角色仍控制是否有对应操作权限。
- 同时核对范围稳定标识、数据源及规范化后的原始系统条件，确认是未经改写的系统租户范围。仅凭 `key=tenant` 不能替换：管理员可能修改了其内容。改写过的范围作为自定义 ACL 保留，在迁移预览中列出；需要管理员明确处理，不能自动放宽。
- 管理员自定义的数据范围完整保留并取交集；只约束本人的业务 ACL 不能被模型自动放宽。
- 未迁移表保持其旧含义。迁移预览需提示仍会限制数据的自定义 ACL，避免把角色限制误诊为模型失效。

委托必须在 ACL 条件与请求筛选合并之前处理，保留服务端确认的范围来源标记，再按当前表的配置版本选择执行方式。不能在租户中间件中扫描已经合并的过滤并删除 `tenantId` 条件，也不能仅在应用启动时决定该表是否已迁移，否则会误删业务条件或使在线迁移失效。

工作流的人工操作使用真实操作者身份；自动数据节点使用其既有、服务端确认的执行身份及租户上下文。第一版不改变既有系统工作流与人类角色 ACL 的关系，但两者涉及的业务数据范围都必须接入 G/V，不得保留业务表旧租户过滤旁路。缺少新规则需要的身份时明确拒绝或报告配置问题，不能猜成根租户管理员。

流程定义、执行记录、审批待办有各自的产品权限，不能因为能读业务单据就自动开放流程管理。它们与业务数据读取分别核对，保留历史审批恢复、重试上下文和可选模块加载的已有修复。

定时业务扫描使用原有任务分派及实际归属范围，与 G 共同约束，V 不参与分派。导出 Worker 在开始执行时重新检查当前规则及权限，保存的上下文不能永久冻结旧授权。

## 11. 管理页面与公共接口

数据表列表显示归属字段管理状态、归属性规则数量、可见性规则数量及配置入口。编辑弹窗只有两个规则分区，使用同一编辑器。指定租户只是条件编辑器中的一个选项，没有额外的“哪些租户可访问”名单控件。

历史数据原有设置迁移成规则模板，界面可以提供“历史数据只读”“允许首次编辑认领”的快捷配置。快捷配置实际创建或修改规则，不保存第二份独立权限状态。共享、本租户、父级访问也采用同样方式。

管理员可以选取样例记录和访问者，预览“不可访问”“可查看”“具有归属性范围”，同时显示仍受哪些角色限制。配置保存使用 `revision` 做并发检查，保存期间禁止编辑同一份配置。所有新增文案和错误同步语言文件。

保存时先完成全部校验，再以旧 `revision` 为条件原子更新整份配置；冲突返回 409，不覆盖他人修改。请求内固定配置快照；保存成功后后续请求及后台新执行读取新版本，多实例不能只靠进程内缓存传播。权限结果默认不做跨请求缓存，编译结构可按数据源、表及配置版本缓存。删除最后一条规则或将所有归属性规则停用前，预览明确提示会失去对应范围，不能自行补一条全范围规则。

当前 `module-collection` 的更新 Hook 只明确在本进程提交后调用 `loadRuntimeOptions`，不是新模型跨进程立即生效的保证。首版由统一服务在请求开始后、首次使用规则时从主库读取权威配置，请求内复用；涉及多个表时按查询计划批量加载。运行时 `collection.options` 和消息通知可以加速刷新，但不能作为权限配置的唯一来源，不能从有延迟的只读副本取得授权版本。

保存沿用集合元数据记录：事务中锁定该行，检查 `revision`，合并当前最新 `options` 的 `tenantAccess`，经原有 Repository 保存，保留其他配置及提交后 Hook。已有通用集合更新、外部数据源配置更新和新配置入口，都必须走同一校验与版本检查，不能存在绕过入口。外部数据源缺少配置行时，先按其稳定唯一标识建行，再处理首次版本竞争。配置成功提交后才发刷新通知。请求开始计算权限后沿用其配置快照，撤权不追溯取消已在执行的请求；新请求必须读取新版本。

普通表配置更新未提供 `tenantAccess` 时保留原值，不把遗漏字段解释成停用模型。规则为空、配置格式损坏或配置加载失败都不能回退旧机制；切回旧机制只能走明确的管理员回退操作，校验版本并恢复已保存的旧配置。配置提交记录保存操作者、时间及修改前后版本，方便定位权限变化；预览只读，不触发迁移、认领或业务工作流。

公共服务的建议契约：

- `resolveScopes`：输入可信身份、数据源、表及执行事务，返回同一规则版本的 G、V、合并读取范围及归属元信息。关系型 G 的租户层级等授权事实必须在写事务内读取，不得复用事务外预先计算的层级列表。
- `scopeQuery`：将范围与原始 ACL、请求条件结合，返回适配器查询计划。查询计划不能从客户端提交。
- `authorizeMutation`：在实际事务内检查待写对象、现有记录及关系变化；使用 G，并保留归属及认领约束。
- `explain`：只供规则管理员预览命中原因，不向无权限用户泄露原本不可见的数据。

普通资源、工作流、图表和导出必须调用这些公共契约，不复制分类逻辑。服务不存在时，仅插件确实未启用才沿用无插件行为；服务异常不能默默执行无约束查询。

文件受控下载按读取范围处理。公开存储 URL 不具备按身份撤权能力，应明确提示该存储不支持文件内容隔离，不能仅检查附件元数据就宣布文件隔离已完成。

单值 BelongsTo 关联增加有限页批量展开服务：一次校验最多 1000 个明确来源主键，一次查询去重后的目标主键。来源和目标分别执行自己的 G/V 与 ACL；目标不可读、不存在或外键为空时该项返回 `null`，来源记录保留。仅返回入口已授权的明确物理字段，内部配对主键、未选字段及虚拟 getter 不返回；共享目标不会继承来源表的租户条件。20 条和 100 条来源的 SQL 次数相同。详见 [单值关联批量展开计划](../plans/2026-10-14-tenant-access-control-belongs-to-expansion.md)。本服务仍未接入业务，关联筛选排序及配置界面仍需后续实施。

HasMany/HasOne 增加同库不同单主键模型的有限页批量展开服务：按真实目标外键分组，来源与目标分别满足 G/V 和 ACL；隐藏目标返回空数组或 `null`，不丢失可读来源。仅投影明确授权的物理字段，按目标主键稳定排序；不支持每来源自定义分页或排序，单次可读目标超过 10000 时整体拒绝，HasOne 多个可读目标也拒绝。两类展开共用元数据守卫，只检查当前规则实际引用的模型、关联和中间表，避免扫描无关表。详见 [一对多和一对一批量展开计划](../plans/2026-10-14-tenant-access-control-target-expansion.md)。仍未接入业务入口，关联筛选排序与业务试点尚未完成。

多对多增加内部有限页批量展开：来源、目标和中间表分别满足自己的 G/V 与 ACL，来源校验后在数据库内连接可读目标及去重后的可读连接键。隐藏目标或连接返回空数组，可读来源保留；重复连接不扩增目标，同一目标可以分别出现在多个来源下。仅返回明确授权的物理目标字段，保留数据库类型，不返回中间记录或内部配对键。最多输入 1000 个来源，单次超过 10000 对可读来源/目标时整体拒绝；不支持每来源自定义分页、排序或占位符。详见 [多对多批量展开计划](../plans/2026-10-14-tenant-access-control-many-to-many-expansion.md)。仍未接入业务入口，关联筛选排序、配置界面和真实业务试点尚未完成。

单跳关联存在性筛选增加内部 `AccessAssociationFilterService.scopeRoots`：BelongsTo、HasMany、HasOne、BelongsToMany 都在来源 G/V 与 ACL 内筛选，正向只匹配可读目标及可读中间记录，反向只表示没有可读匹配。NULL 外键、隐藏目标和隐藏连接不会泄露关联值；相关 `EXISTS` 不扩增根记录计数、分页或金额。默认范围、关联 scope、软删除独立保留，授权规则自身的关系事实不递归附加用户读取权限。计划调用方必须在数据库执行前后调用 `assertCurrent()`；入口仍负责操作、字段 ACL 与条件解析。详见 [关联存在性筛选计划](../plans/2026-10-14-tenant-access-control-association-filter.md)。

内部筛选树进一步支持 AND、OR、NOT 及四类关系的多层筛选，旧单跳接口委托同一实现。每个目标与中间表独立应用读取范围，同一关联节点的多个条件固定匹配同一目标记录；根权限始终位于整棵请求筛选之外。只投影连接键的派生查询支持路径绕回已经出现过的表，不扩增根记录或按行查询权限。完整树在首次异步操作前校验和快照，限制 100 个节点、8 层，拒绝缺失配置、绑定冲突和无效输入。详见 [组合与多层关联筛选计划](../plans/2026-10-14-tenant-access-control-filter-tree.md)。

另增加内部 `AccessRequestFilterParser`，将受限的 JSON 字段条件、逻辑组合、点路径和嵌套关联转为上述筛选树，字段运算符复用核心 `FilterParser`。来源和每一跳关联字段、每个关联目标及多对多中间表都需要服务端读取授权；未知操作符、未授权字段、JSON/数组字段、日期快捷操作符、坏路径及不安全输入明确拒绝。同一个对象内同一关联的条件递归合并匹配同一行；逻辑、存在性和普通条件之间的重叠关联路径拒绝，以免不同条件意外匹配不同关联行。`$exists`/`$notExists` 表示可读关联的存在与否，关联普通字段则沿用核心标量语义。快照拒绝对象与数组访问器，另限制点路径和关联深度。该解析器尚未接入资源 API 或业务页面，入口授权适配、关联排序、日期及扩展运算符、未迁移表兼容、真实业务性能仍待后续阶段。详见 [请求筛选解析计划](../plans/2026-10-14-tenant-access-control-request-filter.md)。

内部 `AccessSortService` 进一步支持根物理标量字段及最多 3 跳 BelongsTo 排序。根记录、每个目标和每跳关联字段分别执行 G/V 与角色授权；默认 scope、关联 scope、软删除和隐藏目标均正确限制排序值。不可读、缺失或空外键目标按 NULL 排在末尾，以根主键稳定分页；使用相关标量子查询，不扩增根记录。列表计划与计数/根金额汇总计划共用根谓词，但后者排除仅排序使用的目标绑定。HasOne、多值关系、自关联和非标量字段明确拒绝。详见 [单值关联排序计划](../plans/2026-10-15-tenant-access-control-sort.md)。仍未接入资源 API，其他排序类型、入口授权适配及真实业务性能仍需完成。

内部 `AccessReadService` 将请求筛选、权限范围、单值关联排序和实际根模型读取串为统一的列表、详情、计数与根数值合计。四类操作共用筛选解析与 G/V、角色、默认范围和软删除条件；列表/详情只返回明确授权的物理字段，直接读取数据值，省略未选主键与虚拟 getter。每次读取在首次异步查询前固定所有路径授权，查询前后检查配置阶段及元数据；排序先同步准备，再组合已编译的筛选。SQL 参数名提前预留而不附加未使用的值，避免筛选与排序互相冲突；较大 JSON 输出不受输入校验大小限制。分页默认 20、最多 1000 条，详情不可读或不存在均返回 `null`。详见 [统一根记录读取计划](../plans/2026-10-15-tenant-access-control-reads.md)。仍未接入资源 API 或业务页面，关联展开组装、入口 ACL 适配及业务性能验收尚需完成。

内部 `AccessReadGrantAdapter` 将入口已完成操作授权、固定范围合并及变量解析的最终权限转为读取 grant。它保留物理字段和单跳关联字段限制，明确空字段不扩大为全部；角色条件可使用隐藏根字段，但不扩大输出字段。每张来源、目标及中间表仍由入口分别授权，转换器不重做角色判断、不递归添加关联 ACL。根字段逻辑条件先折叠 TRUE / FALSE 常量，避免 ORM 忽略空分组后扩大权限；稳定表身份、未解析变量及未知权限参数严格检查。原始 `capture` 仅编译根字段角色条件，关联型条件需使用下述带生命周期检查的 `capturePlan`；嵌套 appends、日期快捷条件等仍明确拒绝。详见 [读取入口权限转换计划](../plans/2026-10-15-tenant-access-control-read-grants.md)。仍未注册资源或切换业务入口；完整角色入口适配、核心扩展点发版升级及逐表启用检查仍需完成。

关联型角色数据条件另增加独立内部 `AccessRoleFilterCompiler`：接收入口已完成变量解析的 JSON 条件，复用受限字段操作符和关系解析，四类关联及多层路径编译为相关 `EXISTS`。这里的关联是内部授权事实，不递归附加目标 G/V 或读取 ACL，也不返回关联数据；目标和中间表的默认范围、关联 scope、软删除仍保留。同一关联对象的条件匹配同一行，重复连接不重复计数；共享目标无需租户列。支持真实非主键关联键和物理列名、回环路径与逻辑空分组；生成别名按大小写不敏感避让，执行前后检查稳定身份、实际模型及关系元数据。详见 [关联角色条件编译计划](../plans/2026-10-15-tenant-access-control-role-filters.md)。编译器提供独立 `where` / `assertCurrent()` 计划，调用方必须检查生命周期，不可直接当作可读字段授权。

内部 `AccessEntryReadService` 进一步把最终入口权限、关联角色条件和统一根读取接起来。入口根据本次操作种类及可信用户/租户上下文，分别提供来源、请求关联目标和中间表的最终操作授权；角色条件与 G/V、用户筛选始终相交，四类读取使用一致范围。`AccessReadGrantAdapter.capturePlan` 校验原始权限描述符后编译条件，并将生命周期检查与纯数据 grant 分开；旧 `capture` 仍拒绝关联型角色条件。检查集逐次操作独立，首次异步操作前固定授权，筛选排序及实际查询前后检查所有授权事实元数据，避免并发请求混用或查询期间关系变化后返回结果。字段与 appends 限制不因转换而扩大，内部授权事实不作为用户可筛选、可排序或可输出的数据。详见 [读取入口角色条件接入计划](../plans/2026-10-15-tenant-access-control-entry-reads.md)。仍未注册资源或启用业务页面；日期快捷条件、嵌套 appends、关联展开组装、核心扩展点接入及真实业务验收尚需完成。

同一入口服务增加 `expandBelongsTo`，把最终来源/目标角色权限与现有单值批量展开组合。来源操作及关联字段、目标操作及明确物理输出字段都要授权；来源和目标各自满足 G/V 与角色行范围。隐藏目标返回 `null`，可读来源保留，批内有隐藏来源整体拒绝。请求只能选择单跳已登记关联、最多 1000 个来源主键、目标字段及事务；原始 where/bind、嵌套 appends、占位来源或坏输入明确拒绝。身份与元数据来自登记模型和可信解析器，全部权限在首次异步调用前快照，角色事实与关联定义在查询前后统一复核；不同身份的并发展开互不复用授权。读取不认领历史数据，较大合法 JSON 输出不套输入限制，20 条和 100 条来源的权限查询次数相同。详见 [单值展开入口权限接入计划](../plans/2026-10-15-tenant-access-control-entry-expansion.md)。仍未启用业务；多值展开入口、嵌套关系组装及其他剩余接入工作继续分阶段完成。

该入口再增加 `expandTargetForeignKey`（HasMany/HasOne）与 `expandManyToMany`（BelongsToMany），三类展开复用同一输入、来源操作/关联字段、目标操作/物理字段检查。多对多按真实登记 through 模型和 `[关联名, '$through']` 路径另取中间表操作授权与角色行范围，中间字段可授权为空，不输出中间记录或内部配对键。来源、目标和连接独立满足 G/V 与角色条件；隐藏目标或连接返回空数组，HasOne 返回单条或 `null`，隐藏来源整体拒绝。所有权限在首个 await 前固定，展开服务在异步准备及 SQL 后复核角色事实、关系、配置与模型；保留原有 HasOne 基数、1000 来源及 10000 目标/配对上限。共享目标和连接不要求租户列，读取历史数据不认领，事务及并发身份独立，20/100 来源查询次数一致。两类输出同步修复合法大 JSON 误套输入限制。详见 [多值展开入口权限接入计划](../plans/2026-10-15-tenant-access-control-entry-multi-expansion.md)。仍未注册业务资源，嵌套 appends 组装、其他入口适配及真实业务验收尚需完成。

内部入口增加 `listExpanded` / `getExpanded`，将根记录筛选、排序、分页和四类单层关联展开组合为同一读取操作。最多选择 20 个直接关联及各自的明确物理字段；根查询取得内部配对主键，但仅输出获准字段，允许只请求关联数据。来源、全部目标和中间表授权及实际规则依赖元数据在首次异步调用前固定，根筛选排序复用同一路径授权；任一关联的配置阶段或元数据变化都拒绝整份结果。隐藏关联返回空值而保留可读根记录，事务贯穿全部查询，不认领历史数据；20/100 条来源的 SQL 次数一致。请求根字段、排序及筛选先按原始输入校验再快照，保留普通读取对特殊数组原型的拒绝。详见 [列表与详情单层关联组装计划](../plans/2026-10-15-tenant-access-control-expanded-reads.md)。仍未注册业务资源或启用页面；嵌套 appends、日期扩展条件、其他入口适配和真实业务试点继续分阶段完成。

上述内部组装进一步支持最多三层、整棵树共 20 个关联。每层按完整路径固定自己的目标、关联字段及中间表授权和元数据；中间层允许只选择关联，隐藏中间项保留为空，不能借下一层展开泄露其内容。三类展开共用内部 `{ key, values }` 配对页，隐藏主键仅用于拼接；同一路径目标去重后整批成为下一层来源，最多 10000 个内部来源键，原有 `load` 的返回字段和 1000 来源上限保留。整份响应最多 100000 个记录位置，共享子树按实际重复序列化次数计数；查询次数仍按路径而非行数增长。详见 [多层关联组装计划](../plans/2026-10-15-tenant-access-control-nested-expansion.md)。仍未注册业务入口；框架 appends 参数转换、日期扩展条件、其他入口适配和真实业务试点尚需完成。

内部入口增加 `listSelected` / `getSelected`，将框架 `fields`、`appends`、`except` 的普通点路径转成明确物理字段和上述三层/20 节点展开树。默认字段只取当前路径已授权字段，不自动展开关联；显式字段越权拒绝，裸关联采用默认字段，排除仅影响默认字段。支持的投影规则与真实核心 Repository 查询选项对照验证。字段选择、筛选、排序和展开共用操作内路径授权；根参数描述符及选择列表在权限回调前捕获，保留原始筛选、排序的严格输入校验。虚拟字段、跨库关系、括号选项、通配符及裸关联排除仍明确拒绝。详见 [框架读取字段选择转换计划](../plans/2026-10-16-tenant-access-control-read-selection.md)。这不是完整资源参数适配器，分页、排序和详情键仍采用内部契约；尚未注册资源或启用业务。实际资源/核心入口接入、最终 ACL 的嵌套 appends 与日期条件、其他入口及真实业务验收仍需完成。

内部入口再增加 `listFromParams` / `getFromParams`，转换已解析的框架分页参数和详情目标键，复用上述字段选择及统一读取链。主库默认第 1 页、每页 20 条，支持规范整数及数字字符串；排序数组先严格校验，逗号字符串可转换为数组。分页上限沿用内部服务，未分页与树查询明确拒绝；事务从服务端独立传入，不接受请求提供的授权、SQL 或事务。详情当前仅支持核心目标键等于唯一主键的模型，查询前后复核，避免把业务编号误当主键查错记录。详见 [页面读取参数转换计划](../plans/2026-10-16-tenant-access-control-resource-params.md)。返回值仍为数组或单条/null；完整分页响应及计数、业务目标键、实际资源路由、其他入口和真实业务验收仍待接入，尚未切换业务行为。

内部入口增加 `listPageFromParams`，返回核心主库分页形状 `{ rows, count, page, pageSize, totalPage }`。列表与总数复用一次根读取计划及同一路径授权，计数保留根筛选，排除分页、展开重复及仅排序使用的目标条件和绑定；空页保留总数，无匹配时总页数为 0。普通分页不读取内部配对主键，不额外施加关联拼接的键长度限制；含关联时沿用三层/20 节点组装及输出上限。事务贯穿列表、计数和展开，没有事务时不承诺各 SQL 共享同一时刻的数据快照。查询及结果组装前后仍校验权限阶段和元数据，旧 list/get 返回值及查询次数不变。详见 [完整分页结果计划](../plans/2026-10-16-tenant-access-control-paged-results.md)。尚未注册资源 API、启用业务页面或修改业务配置；业务目标键、最终 ACL 适配、日期条件及真实业务验收仍待完成。

`getFromParams` 进一步按核心 `collection.filterTargetKey` 的有效物理字段定位，支持主键之外的单个字符串、文本、UUID 和整数字段。入口捕获目标字段后传入内部读取链，请求不能指定字段；定位谓词始终与角色、G/V 及用户筛选相交。隐藏定位字段不会因此获得输出或用户筛选权限，展开继续使用真实主键配对。非主键字符串及 UUID 保留原值，由数据库决定比较语义，整数文本规范化且不丢大整数精度；旧内部主键读取和配对键限制不变。目标字段配置及元数据在准备、查询和展开前后复核，日期、JSON、虚拟字段及复合主键仍明确拒绝。详见 [详情目标键适配计划](../plans/2026-10-16-tenant-access-control-detail-target-key.md)。尚未注册业务接口或修改业务配置；最终 ACL、日期扩展条件、其他入口及真实业务验收仍待完成。

## 13. 第一阶段的具体原型与验收数据

第一阶段只在独立测试库验证条件、查询和事务能力，不修改现有业务表、不启用生产规则。SQLite 用于条件单测；PostgreSQL 用于实际 SQL、计划和并发验证，不能用 SQLite 通过代替后者。

建立总部 H、分公司 B、另一分公司 C，B 和 C 都是 H 的下级。测试单据包含 `tenantId`、金额和参与方关系；每个参与方有明确的业务租户和查看标记。这里的名称和字段仅是测试样例，不是框架内置业务规则。

配置 G 为“记录归属等于当前租户”；配置 V 为“存在同一个参与方，其业务租户等于当前租户，且查看标记为真”。测试角色先使用等价的读写 ACL，随后单独叠加角色限制。

| 单据 | 实际归属 | 金额 | 参与方 |
| --- | --- | --- | --- |
| D1 | H | 100 | B 可查看，重复关联另一项 B 可查看 |
| D2 | H | 200 | 无 |
| D3 | B | 300 | 无 |
| D4 | C | 400 | 无 |
| D5 | 无归属 | 500 | 无 |
| D6 | H | 600 | B 不可查看，C 可查看 |

必须先取得以下确定结果：

| 访问者 | 列表、详情、导出允许的单据 | 总数 | 根记录金额合计 | 允许修改的单据 |
| --- | --- | --- | --- | --- |
| H | D1、D2、D6 | 3 | 900 | D1、D2、D6 |
| B | D1、D3 | 2 | 400 | D3 |
| C | D4、D6 | 2 | 1000 | D4 |

D1 的多项匹配不能重复计数；B 不能把 D6 上两个不同参与方的条件拼成一次匹配。默认没有历史规则，因此任何租户都不能读取 D5。追加父级归属性模板后，H 可以访问并修改 D3、D4，但它们仍归属 B、C。

查询编译先验证下列形状，再决定最小核心扩展。授权关系使用相关 `EXISTS`，不加载全部关联 ID，也不使用会扩增根记录的权限 JOIN：

```sql
-- 示意：参数绑定和表别名均由服务端编译器生成。
WHERE (既有角色数据条件)
  AND (
    单据.tenantId = :currentTenant
    OR EXISTS (
      SELECT 1 FROM 参与方
      WHERE 参与方.单据ID = 单据.id
        AND 参与方.业务租户 = :currentTenant
        AND 参与方.查看标记 = TRUE
    )
  )
  AND (用户请求筛选条件)
```

列表分页、计数和根记录求和必须复用相同根记录条件。参与方索引由关联外键及条件列的实际查询计划确定，不能为了通过样例擅自给真实业务表建索引。不同关系深度与数据量下记录 SQL 次数和计划；权限查询数量可以随请求涉及的关系路径增加，不能随返回记录数增加。

在上述确定集合上继续验证以下边界，每一项都要有独立断言：

1. **角色限制**：B 的 ACL 再限制“仅本人创建”，D1 不符合时仍不可读；无更新操作权限时 D3 仍不可修改。未经改写的内置租户范围可以委托模型，改写过的同名同 key 范围不得自动替换。
2. **空值与上下文**：NULL 字段的不等于及取反不能意外放行；显式 `isNull` 可以匹配。缺少规则需要的租户或用户变量时明确失败；不依赖这些变量的共享模板保持可用。
3. **关联展开及筛选**：给可读单据挂不可读项目，单据保留、项目返回空；以隐藏项目字段做筛选、排序或汇总时不得读取隐藏值。授权所需的参与方事实可内部计算，但不能因此出现在响应中。
4. **实际写入位置**：B 不能嵌套修改 D1；可引用允许读取的目标且不改变目标。HasMany `set` 隐式解绑的旧目标也检查 G；目标有业务字段的中间表及级联删除分别检查实际写入对象。
5. **新增与状态变化**：只有 V 不能新增；伪造输入不能使无权旧记录变得可改；“草稿可编辑”正常提交成功后允许退出原编辑范围，接口不能因回读失败报成执行失败。
6. **历史认领**：为 D5 增加历史 V 后只读，增加历史 G 后首次允许编辑者认领；并发认领只成功一次，另一方重新按最新归属判断。仅引用不认领，不能直接删除未归属单据。
7. **关系并发**：两个数据库连接交错执行授权关系撤销及业务写入，覆盖正向存在、否定存在和租户层级变化。结果必须能解释为合法串行顺序，冲突完整回滚且不发重复通知；已完成撤权后的新写入明确拒绝。
8. **配置并发**：两位管理员用同一旧版本保存，只允许一次成功；其他 `options` 不丢失。两个独立应用实例分别请求，保存成功后的新请求都读取新规则，不能靠同一进程共享缓存让测试假通过。
9. **入口一致性**：同一身份的列表、计数、根记录汇总、图表、导出和工作流查询得到相同集合。用户界面关联路径含 `/_/`、外部数据源有同名表时仍选择正确目标和配置。
10. **归属型定时任务**：H、B、C 各自只扫描其实际归属范围内符合 G 的任务数据，D1 的 V 不使 B 再处理一次，生成数据不被误挂到可见者租户。

原型通过后才接入一张本地业务试点表，并完整验证该表的全部入口，再制作规则管理界面和逐表迁移。若查询或事务原型无法满足要求，先调整适配层设计，不以放宽校验或恢复全局关联拦截的方式推进上线。
